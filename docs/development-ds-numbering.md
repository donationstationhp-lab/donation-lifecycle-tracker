# Development DS correction and numeric numbering

The owner explicitly authorized relabeling fourteen pre-pilot August inventory
records into the DS-L family. This supersedes the old Development-only 6396
high-water rule. It does not authorize any Production data correction.

Mappings: DS-1001 through DS-1010 become DS-L-1001 through DS-L-1010;
DS-2558, DS-2590, DS-5038 and DS-6395 become their DS-L equivalents.
UUIDs, relationships, classifications, original creation dates and existing
external references remain unchanged. Original DS strings are permanent aliases.
Each changed inventory record gets a stage-history note with the requested
October 16, 2026 correction date; the history timestamp is the actual execution
time, not a fabricated October 16 timestamp.

## Numeric representation and uniqueness

Canonical ds_number is PostgreSQL bigint on inventory and identity records.
It is returned as an exact decimal string, never a JavaScript floating-point
number. Legacy and external identities have null canonical ds_number.
Database triggers derive the field from the canonical text ID, preventing a
caller from supplying a mismatched number.

item_ds_reservations has one primary-key reservation per numeric DS value.
Inventory and registry representations of the same UUID may share that value;
another UUID may not claim it, including with different zero padding.
Alias-only and ambiguous imported DS labels reserve numbers without assigning
a canonical owner. They remain reviewable, never silently merged or allocated.
Deleting or relabeling an item does not release its reservations.

Ordinary allocation locks item_ds, reconciles against the highest current
canonical inventory/identity DS number, preserves a higher saved counter, and
skips every reservation, alias and source snapshot at the candidate number.
DS-L, EXT and aliases do not raise the canonical floor.
Formatting pads to at least four digits: DS-9999, DS-10000, DS-10001.
There is no artificial 9999 cap. PostgreSQL bigint's natural signed 64-bit
storage limit still applies; there is no precision-losing Number conversion.
Claim tracking retains its existing six-digit rules and allocation behavior.

The explicitly authorized correction lowers the Development counter once to
the first unreserved number after the highest canonical identity (expected 6).
It refuses missing/ambiguous August records, identity conflicts, any occupied
new DS-L label, and partially relabeled batches. A rerun verifies aliases and
does not lower a counter or add duplicate history.

## Applying schema and data

The additive schema helper and constraint installer live in the db library.
They are explicit migration operations, **not application-startup DDL**.
Tests install the same constraints in isolated synthetic schemas.

The one-time script is:

```sh
NODE_ENV=development pnpm --filter @workspace/api-server exec tsx \
  src/scripts/correct-development-ds.ts --confirm-development \
  --development-fingerprint=<fresh-read-only-development-fingerprint>
```

Obtain the nonsecret fingerprint from the explicitly selected Development
connection using:

```sql
SELECT md5(coalesce(string_agg(id,',' ORDER BY id),'')) AS fingerprint
FROM donation_items;
```

The command refuses a deployment process, requires explicit confirmation, and
checks its database against this independently obtained Development fingerprint.
Environment metadata alone is not sufficient evidence of the database target.
The complete relabel, numeric backfill, constraint installation and counter
correction run transactionally. A schema-only preparation flag adds columns,
widening and indexes without changing application rows, for fixture testing.
No Notion call, Sheets event, ID allocation or account migration is performed.

Do not run this command against Production. Publishing the code/schema later
does not itself authorize relabeling Production data. Provider-managed
production schema rollout and installation of the additional database triggers
must be reviewed together before any later published rollout.

Old account-move exports and manifests are intentionally not regenerated by
this task and predate the correction; they are not a corrected baseline.
